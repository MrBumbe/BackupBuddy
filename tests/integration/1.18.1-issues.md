## ISSUE-009
Step: D/E — cluster formation (Björn's view after Carina joins)
Symptom: After all three nodes complete their wizards, Björn's dashboard shows
  only 2 cluster members (Björn + Anders). Anders and Carina both show 3 members.
  Björn was not notified when Carina joined the cluster.
API response: Björn /api/dashboard → total_members: 2, online_count: 2
  Anders /api/dashboard → total_members: 3, online_count: 3
  Carina /api/dashboard → total_members: 3, online_count: 3
Blocking: no — backups can proceed (Tahoe+Introducer topology still works),
  but Björn's UI is misleading.
Root cause hypothesis: When a new node joins via the introducer (Anders), Anders
  does not push the updated member list to existing members (Björn). The next
  time Björn contacts the introducer or vice-versa, the list may update.
  This is likely the same gap that was noted in ADR-021 for vote propagation —
  cluster state is not pushed to all peers on change.
Design finding: adding cluster member push on join (similar to vote propagation
  in ADR-021) would fix this. Alternatively, each node could poll the introducer
  periodically for the member list.

## ISSUE-007

Symptom: After creating /mnt/buddy-storage as root, wizard rejects with:
  "Path is not writable: '/mnt/buddy-storage'"
  Directory is owned by root:root with 0755 — not writable by the
  'backupbuddy' service user (uid=999).
Blocking: no (chmod/chown fixes it)
Fix applied: `chown backupbuddy:backupbuddy /mnt/buddy-storage` on each node.
Design finding: INSTALL.md §4 Step 3 must either:
  (a) Tell the user to create the dir AND set ownership:
      `sudo mkdir -p /mnt/buddy-storage && sudo chown backupbuddy:backupbuddy /mnt/buddy-storage`
  (b) Or better: let the wizard create and own the directory itself
      (fixing ISSUE-006 would also fix ISSUE-007).
  The combination of ISSUE-006 + ISSUE-007 means a user creating the dir
  "correctly" per the guide will get two confusing errors before it works.

## ISSUE-004  ← BLOCKING FIX
Step: C2/C4 — gatekeeper service fails to start
Symptom: backup-buddy-gatekeeper.service crashes immediately with:
  ImportError: cannot import name 'BaseReload' from
  'uvicorn.supervisors.basereload'
  (/opt/backup-buddy/.venv/lib/python3.12/site-packages/uvicorn/supervisors/basereload.py)
  Inspection reveals basereload.py is a 0-byte empty file.
Root cause: The Tahoe-LAFS fork (installed with pip install -e) creates empty
  0-byte stub files for all its dependencies, including uvicorn. The install
  script's second pass (`pip install --force-reinstall -r requirements.txt`)
  is supposed to replace these stubs. On the phase-a snapshot, uvicorn's
  basereload.py was not replaced — it remained a 0-byte stub.
  This is a latent fragility in the install process: if the force-reinstall step
  fails partway (network blip, disk pressure, SIGKILL), the user ends up with
  an unbootable gatekeeper and no obvious error at install time.
Blocking: yes — gatekeeper cannot start
Fix applied: ran the installer again on VM 101 (`sudo bash install/gatekeeper.sh`)
  — the idempotent install script re-ran setup_venv() which force-reinstalled
  uvicorn, replacing the empty stub with a real package.
Restarted test? No — running the installer IS step C2 in the test (what a real
  user does). This is not a code-level fix.
Design finding: the installer should verify that no 0-byte files exist in the venv
  after the force-reinstall step, and fail with a clear error if they do.

## ISSUE-013
Step: H (resilience test) — restore with one gatekeeper offline
Symptom: Stopping the introducer node (Anders) causes restores on Björn to fail
  immediately with `TahoeError: download failed (HTTP 410)`.
  With adaptive profile (k=1, n=3), only 1-of-3 shares is needed, so Björn and
  Carina's storage nodes alone should be sufficient. But Björn's Tahoe client
  loses all grid connectivity the moment the introducer process stops.
  The Tahoe client returns HTTP 410 (Gone) — indicating it cannot locate any of
  the 3 shares for the file, even though 2 storage nodes are still running.
Blocking: no — Anders was restarted; normal restores all completed successfully.
Fix applied: restarted Anders; resilience test outcome logged only.
Root cause: Tahoe clients discover storage servers via the introducer. When the
  introducer goes down, the client cannot maintain or refresh its server list, so
  all download attempts fail. There is no persistent storage-server cache on the
  client side.
Design finding: this is a significant resilience gap. Losing the introducer node
  makes the entire Tahoe grid unavailable for downloads, regardless of how many
  storage nodes are up. Mitigations:
  (a) Tahoe clients should cache known storage server FURLs locally, allowing
      them to attempt downloads using cached server addresses after introducer loss.
  (b) Alternatively, each gatekeeper could act as its own introducer (a relay model),
      so there is no single introducer point of failure.
  (c) Or: promote one additional node as a secondary introducer.

## ISSUE-012
Step: G (restore) — restore dest_path must be a full file path
Symptom: Restore jobs returned `status: failed` with "Restore failed. Check the
  gatekeeper log for details." Gatekeeper log shows:
  `PermissionError: [Errno 13] Permission denied:
  '/tmp/bb_restore_lwkhvlla/restore.tmp' -> '/tmp/restored/anders'`
Root cause (two compounding factors):
  (a) dest_path must be the full target file path (e.g. /tmp/restored/file.iso).
      The restore code does an atomic rename from a temp file to exactly dest_path.
      Passing a directory path causes the rename to fail.
  (b) /tmp/restored was created as root:root 755. The backupbuddy service user
      (uid=999) has no write access, so the rename fails with EACCES before the
      directory-vs-file type check.
Blocking: no (fixed by recreating dest dir with chmod 777 and using full file paths)
Fix applied: `rm -rf /tmp/restored && mkdir -p /tmp/restored && chmod 777 /tmp/restored`
  then resubmitted with dest_path = /tmp/restored/<filename>.
Design finding:
  (a) API documentation (or INSTALL.md) should make explicit that dest_path is
      the full output file path, not a destination directory.
  (b) The restore code should detect when dest_path is an existing directory and
      fall back to writing <dest_path>/<original_filename>, matching the behaviour
      users expect from tools like `cp file /dir/`.
  (c) The error message shown to the user ("Restore failed. Check the gatekeeper log")
      is not actionable — it should surface the actual cause (permission denied /
      invalid dest_path) directly in the API response.
