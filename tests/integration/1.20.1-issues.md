## ISSUE-001 — Carina join cascade: PermissionError on api_auth_token

**Step:** E (wizard step 5 for Carina)
**Blocking:** YES (required manual workaround)
**Status:** Resolved (workaround applied)

**Description:**
Carina's join cascade failed because `/var/lib/backup-buddy/tahoe/storage_node/private/api_auth_token`
was owned by `root:root` instead of `backupbuddy:backupbuddy`. The Tahoe storage node process
(running as `backupbuddy`) could not write to this file and crashed on startup with:
```
PermissionError: [Errno 13] Permission denied: .../private/api_auth_token
```

Root cause: a diagnostic manual `tahoe run` was executed as root during troubleshooting,
which created the file (and several other files) with root ownership.
These files then blocked subsequent cascade attempts.

**Side effects discovered:**
- The join DID succeed on Anders's side (carina-home in members table, invite consumed)
  before the Tahoe crash, leaving invite `year-skies-1` as used=1.
- A retry with a new invite would fail because `carina-home` is already in Anders's members
  table (INSERT raises IntegrityError, not ValueError → 500 from Anders).
- The cascade has an idempotency shortcut: if `root_dir.cap` exists, it skips `initiate_join`
  entirely and proceeds to write gatekeeper.cfg.

**Resolution:**
1. Fix permissions: `chown -R backupbuddy:backupbuddy /var/lib/backup-buddy/tahoe/`
2. Start Tahoe manually as backupbuddy, call `POST /uri?t=mkdir` to create root_dir.cap
3. Write the cap to `/var/lib/backup-buddy/root_dir.cap`
4. Re-run step 5 (cascade skips join/Tahoe, writes gatekeeper.cfg directly)
5. Trigger service restart

**Root issue (separate from diagnostic error):**
In the 1.20.1-v2 session (yesterday), PID 3493's cascade was killed by a SIGTERM while
starting the storage node. The cascade failure left carina-home inserted in Anders's DB
and the invite consumed, with no root_dir.cap written. On restart (PID 4173), the wizard
auto-retried with the same invite (already consumed) → 400. This is a pre-existing issue
unrelated to the permission problem above.

**Note for code review:** `accept_join` calls `consume_invite` before `insert_member`.
If `insert_member` fails (e.g. duplicate node_id), the invite is consumed with no rollback.
Separate issue, not blocking Phase 1.
