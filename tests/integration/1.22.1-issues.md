## ENRADSFIX-001 — Step C2 — Pip warnings in installer output (Anders only)

**Type:** ENRADSFIX  
**Step:** C2 (install gatekeeper on Anders, VM 101)  
**Observed:** The installer produced many `WARNING: Ignoring invalid distribution ~agic-wormhole` lines during the "Installing Python dependencies" phase. These did not appear on Björn or Carina (which had fresh venvs). This is caused by a partially-installed magic-wormhole package left in the venv from a previous test run that was snapshotted into `clean-ubuntu-v2`.

**Expected (INSTALL.md §3):** Clean output with only `[✓]` check lines. No pip warnings.

**Impact:** Cosmetic — the install succeeded. A real user would see alarming spam. The INSTALL.md expected output block does not mention these warnings.

**Root cause:** The `clean-ubuntu-v2` snapshot for VM 101 contains a pre-existing venv with a corrupted `magic_wormhole` package. Fresh installs (VM 102, 103) are clean.

**Fix required:** Two options:
1. Rebuild the `clean-ubuntu-v2` snapshot with a clean venv (or no venv), OR
2. Add pip cleanup step to the installer that removes invalid distributions before installing.

**Status:** Snapshot issue — not fixed inline (requires snapshot rebuild or installer change). Recorded here for follow-up.

## ISSUE-001 — Step F3 — agent-anders-nas (LXC 302) OOM killed on 1 GB file

**Type:** ISSUE  
**Step:** F3 / F4 (Carina agent, large file upload)  
**Observed:** LXC 302 (agent-anders-nas) had 512 MB RAM. The agent reads the entire file into
memory with `Path(file_path).read_bytes()`. For the 1 GB test file, this consumed all available
RAM and the kernel OOM-killed the agent process. Repeated across several restart cycles.

**Root cause:** `read_bytes()` loads the full file into memory. A 1 GB file requires 1 GB of
RAM in the agent process — incompatible with the 512 MB LXC container.

**Workaround applied:** Increased LXC 302 memory to 2048 MB via Proxmox `pct set 302 --memory 2048`.

**Proper fix needed:** Stream large files in chunks instead of `read_bytes()` to avoid the
memory spike. See LARGER FIX below.

**Status:** Resolved for the test with memory increase. Not fixed in code.

## ISSUE-002 — Step F4 — gk-carina (VM 103) OOM killed when receiving 1 GB upload

**Type:** ISSUE  
**Step:** F4 (Carina gatekeeper receives 1 GB fragment)  
**Observed:** gk-carina (VM 103, 2048 MB RAM) was repeatedly OOM-killed when the agent posted
a 1 GB HTTP body. FastAPI reads the full request body into memory. The gatekeeper process was
already using ~1.65 GB (Python + Tahoe), so the 1 GB body pushed total usage past 2 GB.
dmesg confirms: `Out of memory: Killed process ... anon-rss:1693972kB`.

**Root cause:** FastAPI buffers the full request body before the route handler can process it.
With Tahoe and the Python runtime already consuming ~1.65 GB, there is no headroom for a 1 GB body.

**Workaround applied:** Increased VM 103 memory to 4096 MB. After reboot, the gatekeeper could
receive and process the 1 GB upload without OOM.

**Proper fix needed:** The gatekeeper's `/api/agents/fragments` endpoint should stream the
request body incrementally (using FastAPI's `request.stream()` pattern) rather than buffering
the full body with `await request.body()`. This is a LARGER FIX and should be tracked.

**Status:** Resolved for the test with memory increase. Not fixed in code.

## LARGER FIX-001 — Large file streaming (from ISSUE-001 and ISSUE-002)

**Type:** LARGER FIX  
**Related issues:** ISSUE-001, ISSUE-002  
**Summary:** Large file uploads currently load the entire file into memory on both the agent side
(`read_bytes()`) and the gatekeeper side (FastAPI body buffering). This is fragile for files
over ~500 MB on constrained hardware.

**Required changes:**
1. **Agent `_upload_worker`:** Use streaming HTTP upload (`httpx.stream()` with a file-like
   object) instead of `read_bytes()` + bulk POST.
2. **Gatekeeper `/api/agents/fragments`:** Use `request.stream()` to read and write the body
   to `upload_tmp/` incrementally, then pass the temp file path to the fragmenter queue.

**Priority:** Medium — only affects files > ~500 MB on hardware with < 4 GB RAM. For typical
homelab use cases, most backed-up files are well under this threshold.

**Status:** Not implemented. Added to TODO tracking.

## ISSUE-003 — Step F4 — httpx 30s timeout causes OSError for 1 GB uploads

**Type:** ISSUE  
**Step:** F4 (agent upload timeout)  
**Observed:** The `GatekeeperClient` was initialized with `timeout=30.0` (30 seconds). Sending
a 1 GB file over LAN can take >30 seconds, causing `httpx.TimeoutException` which is wrapped as
`IOError`/`OSError`.

**Fix applied:** Changed httpx timeout to `httpx.Timeout(connect=30.0, read=600.0, write=600.0,
pool=30.0)` in `agent/gatekeeper_client.py`. Committed as `fix(agent): increase httpx timeout
for large file uploads`.

**Status:** Fixed in code.

via `private/servers.yaml` cache + Tailscale IPs) was verified by the H resilience test:

That is the correct and complete verification of 1.21.3.

**Resolution:** No action needed. The TODO H-intro procedure may be updated in a future
cleanup to reflect that VM 104 is obsolete in the current architecture.
