ISSUE-1 | cluster/join | medium | VERIFIED on current code (e137b8f3c)

Partial idempotency gap: Fix (C) in join.py covers "used invite + already a member" (returns success), but has NO guard for "fresh/unused invite + already a member". When a node that is already in members table uses a valid NEW invite code, accept_new_member raises IntegrityError (duplicate node_id) because the member row already exists. The invite IS consumed (used=1 in DB) but HTTP 400 is returned to the joiner.

Observed during F-test setup: invite `twice-crush-2` was generated fresh, no expiry set, tested with node_id `test-expire` — joined successfully (HTTP 200). This is correct behavior (test-expire was not already a member). The ISSUE-1 scenario (fresh invite + duplicate node_id) was not directly triggered in this simulation run. Classified as a latent defect.

Expected fix: in accept_join, before calling accept_new_member, check if node_id is already in members table. If yes, skip insert and return success (same as Fix C path). Optionally consume or leave the invite unconsumed.

Context: the scenario arises when a node's join cascade fails partway through (after the initial accept_join call) and retries with a fresh invite code generated by the operator. Fix (C) only handles the exact retry with the same (now used) invite.

ISSUE-2 | gatekeeper/verify + gatekeeper/main | medium | VERIFIED on current code (e137b8f3c)

NightlyVerifier in gatekeeper/verify/nightly.py is fully implemented but not wired into the scheduler in gatekeeper/main.py — `_verify_stub()` is called instead, logging `Verify scheduler: pending implementation (task 1.13.2)`. Must be wired before Phase 1 is declared complete.

Same pattern seen for watcher scheduler (task 1.6.2) and rebalance scheduler (task 1.11.2).

Observed during J5 check: `journalctl -u backup-buddy-gatekeeper | grep -i verify` on gk-anders shows stub log line on every gatekeeper startup.

Expected fix: wire NightlyVerifier into the APScheduler/asyncio task setup in gatekeeper/main.py startup sequence, replacing the `_verify_stub()` call.

ISSUE-3 | agent/watcher + agent/main | medium | VERIFIED on current code (e137b8f3c)

Failed uploads are not retried on the next watcher cycle. When `send_fragment()` raises IOError (e.g. HTTP 507 insufficient disk space), the upload worker logs the error but does not return the file path to the watcher. `FileWatcher._check_file()` returns False for any path already in `self._queued` (watcher.py line 137–138). Since the path is never removed from `_queued` after a failed upload, the file is silently skipped on all subsequent scan cycles.

Observed during L4 test: after unmounting the 100 MB tmpfs from `/var/lib/backup-buddy/upload_tmp/`, disk-guard-test.bin was not retried automatically. An agent restart was required to clear the in-memory `_queued` set, after which the next watcher cycle successfully uploaded the file.

Expected fix: after a failed upload in `_upload_worker()`, remove the file path from `FileWatcher._queued` so the next scan cycle can re-queue it. Requires a thread-safe `dequeue(path)` method on `FileWatcher` (the queue put path runs in the event loop but the watcher scan runs in a thread via `asyncio.to_thread`).
