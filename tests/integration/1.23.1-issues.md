ISSUE-1 | cluster/join | medium | VERIFIED on current code (e137b8f3c)

Partial idempotency gap: Fix (C) in join.py covers "used invite + already a member" (returns success), but has NO guard for "fresh/unused invite + already a member". When a node that is already in members table uses a valid NEW invite code, accept_new_member raises IntegrityError (duplicate node_id) because the member row already exists. The invite IS consumed (used=1 in DB) but HTTP 400 is returned to the joiner.

Observed during F-test setup: invite `twice-crush-2` was generated fresh, no expiry set, tested with node_id `test-expire` — joined successfully (HTTP 200). This is correct behavior (test-expire was not already a member). The ISSUE-1 scenario (fresh invite + duplicate node_id) was not directly triggered in this simulation run. Classified as a latent defect.

Expected fix: in accept_join, before calling accept_new_member, check if node_id is already in members table. If yes, skip insert and return success (same as Fix C path). Optionally consume or leave the invite unconsumed.

Context: the scenario arises when a node's join cascade fails partway through (after the initial accept_join call) and retries with a fresh invite code generated by the operator. Fix (C) only handles the exact retry with the same (now used) invite.
